Product decision: strict two-sided rule

Per the Foreman's ruling, a one-sided match is never exact. The exception that ff66a57 made for the first or latest known message (one matching neighbour, no other copy of the text known when saved) is removed. No edge case was kept. The candidate the work order names (coverage proves the whole conversation is loaded and the anchor recorded "no previous message") cannot be established in this build. Folio has no complete-coverage state: its best coverage level, loaded-only, says outright that "Folio cannot confirm that claude.ai has loaded the whole conversation". So "no neighbour" can never be confirmed again later. A bookmark of the first known message or of the latest message is therefore at most probable ("Not confirmed") or ambiguous, and Open does not jump to it. The copies count is still recorded with new anchors but no longer affects resolution.

Known gaps

  • Live claude.ai behaviour is UNKNOWN.
  • Strict rule: a bookmark of the first known message or of the latest message is never exact ("Not confirmed"; Open does not jump), even after the conversation continues. This includes the outline's ☆ on the latest exchange, which bookmarks the latest reply. Outline and search clicks still reach these messages. Bookmarking the reply again after the next prompt gives a bookmark that can be confirmed. Bookmarks of the first or latest message saved by ff66a57, which could show "Found in this page", now show "Not confirmed".
  • A click on a list drawn before the page changed is followed only if the entry's anchor, as of that list, is exact or changed. The first or latest entry of that list, and entries among identical exchanges, are refused with "The page changed after this list was shown" and must be chosen again from the updated list. A page change that Folio has not yet indexed (it re-reads the page within about a second) also sends a click through these rules.
  • While a reply is being written, a click on that reply (or a heading in it) can be refused: its text changed after the list was drawn, and as the latest message its anchor cannot be confirmed. Clicks on other messages are not affected.
  • Live identity assumes that when every loaded message element still holds the same role and text in the same order, the page still shows the same messages. A page that re-bound all of its loaded elements at once to another run of identical messages would not be detected. Whether claude.ai reuses message elements at all is UNKNOWN.
  • If the message after a bookmarked message changes (the next prompt edited, a later reply regenerated), the bookmark becomes unresolved: Folio cannot tell that from another copy of the same text.
  • A bookmarked message at the edge of what is loaded, whose neighbour on that side was known when saved, is "Not confirmed" until that neighbour loads.
  • Bookmarks of fully identical exchanges (same text and same neighbours) are ambiguous by design; only outline and search clicks can tell them apart.
  • Clicks on a list older than the kept generations (8 recent, plus 2 searches) are refused with a request to choose again or search again.
  • Bookmarks saved by Folio 0.1.0 have no context: ambiguous when a message with the same or a similar opening text is known, otherwise unresolved; they must be bookmarked again.
  • When the loaded window could sit in two equally good places among known messages, Folio keeps only the loaded messages; messages seen earlier are then no longer listed or searchable.
  • Erase all reaches tabs where Folio's content script runs; tabs opened before installation have nothing to erase.
  • Only loaded messages are indexed; other branch versions, images, files and artifacts are not. Chapters are partial. No archive or export of conversations (P1).
  • The real side-panel container, toolbar click, screen readers, theme visuals and JSON download to disk are not covered by automation.
  • No TypeScript type-check was run (no compiler available).
