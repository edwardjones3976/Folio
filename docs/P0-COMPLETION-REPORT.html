Review finding and changes

FindingChangeTests and the result on a12b193
1 (P2) Refresh could turn a detected element mismatch into an exact jump to an unloaded target's duplicateTwo changes, each of which closes the probe on its own.

The refresh fingerprint includes element identity. In src/content/indexer.ts, LiveIndex gives each message element a number (a WeakMap from element to number, cleared with the index). Each loaded message contributes that number to the fingerprint where it used to contribute only "rendered". When the page shows any loaded message in a different element, the fingerprint changes and the revision advances. This covers a re-render, and a window that slid onto an identical run of messages, where the keys stay the same but name other messages. A list drawn before is then from an older generation, so a click on it goes through the full anchor rules. The old generation is no longer overwritten under the same revision.

The refusal is carried through the retry. LiveIndex.target() now reports differs: true when its live() check refused because the page no longer showed what the index held. It also takes a byAnchor argument. With byAnchor, the entry is resolved by its anchor even in the current generation and is reported as stale, so it is never exact by position. go in src/content/main.ts passes byAnchor on the retry after a refusal with differs. So a click that failed the page check is found again only by its anchor, even if the rebuilt index looked unchanged.		Unit, tests/unit/indexer.test.ts, new suite "a changed element mapping invalidates the click":
  • "the review probe: the later Continue, clicked after the window slid back, is not exact to the earlier one". This is the reviewer's probe: two identical pairs, a click on the later prompt, then an older identical pair loads, the earlier pair keeps its elements and the clicked pair is detached. Now it returns stale:true and ambiguous with no element, the same resolution as the saved anchor.

What is stored (unchanged)

The stored bookmark format is unchanged. In memory, the index also keeps a number for each message element it has seen, in a WeakMap, so the page's elements are not kept alive by it. The numbers hold no message content and are dropped with the index (conversation change, Erase all, turning Folio off). Earlier index generations still keep only their message lists, with no element references.

Known gaps

  • Live claude.ai behaviour is UNKNOWN.
  • New in this correction: if claude.ai re-renders message elements without changing their text, each re-render starts a new version of the index. The panel then redraws, and a click on the list drawn just before goes through the anchor rules, so the first or latest entry, and entries among identical exchanges, are refused until they are chosen again from the updated list. How often claude.ai re-renders message elements is UNKNOWN (manual check 10a).
  • When the loaded window slides onto a run of messages identical to the ones it replaced, the window is still placed by text (mergeLoaded is unchanged). The updated list matches what the page shows, but the copies that slid away may not be listed as "not loaded". Clicks on lists drawn before the slide are resolved by their anchors.
  • Strict rule (unchanged): a bookmark of the first known message or of the latest message is never exact ("Not confirmed"; Open does not jump), even after the conversation continues. Outline and search clicks still reach these messages.
  • A click on a list drawn before the page changed is followed only if the entry's anchor, as of that list, is exact or changed. A page change that Folio has not yet indexed (it re-reads the page within about a second) also sends a click through these rules.
  • While a reply is being written, a click on that reply (or a heading in it) can be refused. Clicks on other messages are not affected.
  • Live identity assumes that when every loaded message element is the same element and still holds the same role and text in the same order, the page still shows the same messages. A page that re-bound all of its loaded elements at once to another run of identical messages, keeping every element in place, would not be detected. Whether claude.ai reuses message elements at all is UNKNOWN.
  • If the message after a bookmarked message changes (the next prompt edited, a later reply regenerated), the bookmark becomes unresolved.
  • A bookmarked message at the edge of what is loaded, whose neighbour on that side was known when saved, is "Not confirmed" until that neighbour loads.
  • Bookmarks of fully identical exchanges are ambiguous by design; only outline and search clicks can tell them apart.
  • Clicks on a list older than the kept generations (8 recent, plus 2 searches) are refused with a request to choose again or search again.
  • Bookmarks saved by Folio 0.1.0 have no context: ambiguous or unresolved; they must be bookmarked again.
  • When the loaded window could sit in two equally good places among known messages, Folio keeps only the loaded messages.
  • Erase all reaches tabs where Folio's content script runs; tabs opened before installation have nothing to erase.
  • Only loaded messages are indexed; other branch versions, images, files and artifacts are not. Chapters are partial. No archive or export of conversations (P1).
  • The real side-panel container, toolbar click, screen readers, theme visuals and JSON download to disk are not covered by automation.
  • No TypeScript type-check was run (no compiler available).
