FOLIO — Product & Engineering Contract

Version: 1.0 • Created: 2026-10-29 • Status: Proposed product specification, not evidence of implementation or market validation • Owner: Repository owner

Core mission: Transform unwieldy AI chat conversations into faithfully preserved, searchable, book-like collections of original exchanges. A user must be able to find the exact answer they remember without endless scrolling. FOLIO is not a generic chatbot or another chat sidebar.

1. User problem, initial market, measurable success

The founding pain point is attempting to find a valuable original answer buried hundreds of messages back in a commercial AI chat. Search is often insufficient, long scrolling is tedious, and prompting the model to regenerate the answer loses wording, structure, nuance, and provenance. Initial audience: AI power users, software builders, students, researchers and long-term project owners with large conversations.

Human value: Find, reopen, read, bookmark and organize exact original exchanges. Later AI value: selectively rehydrate relevant, source-linked history into bounded context packets. Do not sacrifice human usefulness to build an elaborate memory engine first.

Competitive baseline: Ophel Atlas and TidyChats already offer navigation, outlines, search, bookmarks, folders and exports. Other chat navigation extensions exist. These are commodity entry features. FOLIO's hypothesized differentiator is the durable conversation-to-book experience: faithful archive, user-editable topical chapters, original chronology, cross-book connections, decision histories and intelligent retrieval. Never claim that a feature is novel, exclusive or superior without a test.

Market velocity: evaluate both present competitive coverage and how quickly incumbents could replicate or saturate this workflow. That is distinct from our engineering delivery speed. Check official competitor changelogs/offerings before each material scope expansion.

2. Immutable product principles

  1. Originals first: preserved source messages are authoritative. Summaries, chapters, renderings and inferred decisions are derived, editable and versioned.
  2. Faithful means qualified: preserve exact accessible text and metadata where supplied; do not claim a complete archive if a provider omits messages, images, edits, attachments, timestamps or reasoning.
  3. One message, multiple structures: organize exchanges topically without erasing chronology; one source message may appear in multiple chapters and books without duplication of its canonical content.
  4. Local-first privacy: no sending conversation text to an external server or model without explicit, granular opt-in. Least-privilege host permissions.
  5. Durability: user-controlled export, backup and offline readability; no dependence on a live provider DOM once a verified archive has been imported.
  6. Honest operation: missing, blocked, truncated, unverified or partial ingestion must be visible. No invented original text or silent regeneration.
  7. Progressive enhancement: navigation without AI, archiving without cloud AI, optional semantic intelligence only after the basics are reliable.

4. P0 user stories and interactions

  1. Open: On a supported long conversation, the user opens the extension panel and sees a compact outline of message clusters. It must remain usable on narrow screens and long histories.
  2. Jump: Clicking any outline entry scrolls to/highlights the corresponding original exchange in the commercial UI; label inaccessible/unloaded targets rather than jumping inaccurately.
  3. Find: Search exact terms in content the extension is authorized to access; show snippet and source location. If only some messages are loaded, state coverage.
  4. Bookmark: Save a stable source-specific reference, title/note and timestamp locally; reopen in the same chat; report unresolved anchors.
  5. Chapters: Build deterministic topic sections from headings, visible conversation structure and user input. AI-generated chapters are optional and must not be necessary for P0; differentiate source-backed and inferred labels.
  6. Settings: Enable/disable on supported sites, choose light/dark/readability options, erase local records, inspect exactly what is stored and exported.

Use explicit feature statuses: working, partial, blocked, not_implemented. Do not present a UI control that implies unsupported capabilities.

5. P1 reader and content model

Reader modes: Book View (chapters, sections, page navigation and comfortable typography); Conversation View (unmodified original chronology and speaker roles); Study View (original content alongside highlights, notes and references).

Canonical entities: Source (provider, import mechanism, source URL and declared coverage); Conversation (stable source ID or derived ID, import revision); Message (source ID, role, sequence, original text, timestamp if provided, structured content/attachment references if supported, completeness marker, digest); Book; Chapter; Section; Membership (many-to-many source span references); Bookmark; Annotation; Decision (claim, evidence spans, scope, temporal status); DerivedSummary (model, prompt/configuration, version, evidence links); ImportRun (counts, missing/error details); ContextPacket (selected sources, token budget and authorization).

Identity: Prefer provider-issued IDs when legitimately available; otherwise derive content-based IDs with source/conversation/ordinal disambiguation. Keep stable deep links where supported, detect changed/missing anchors, never depend solely on transient CSS selectors. Import idempotently; preserve prior snapshots and corrections; never silently overwrite original records with a re-ingest.

Preservation: Original source text stored separately from derived HTML; sanitize rendered imported markup; preserve code blocks and formatting where reliably supplied; preserve speaker distinctions; annotate omissions. User-controlled deletion must actually remove selected personal records from local archive and indexes.

6. Extension architecture and threat model

Recommended P0: TypeScript + Chrome Manifest V3; minimal content script scoped to explicit supported origins, side panel or extension UI, service worker as necessary, browser local storage (not SQLite in the browser extension). No external telemetry by default. Python/FastAPI + SQLite/FTS5 is a possible later local companion for P1+, not a P0 prerequisite.

Site adapters: isolate chat-provider-specific DOM discovery, source mapping, navigation, and coverage checks behind interfaces. Build one robust adapter first. Validate on loaded, partially-loaded, virtualized, edited, and lengthy conversations; when messages are unavailable, report that rather than inventing them. Avoid depending on private/undocumented API endpoints, credential extraction, or automatic scraping of unrelated pages.

Security: explicitly document every permission; never read cookies/tokens or password fields; defend against script injection, malicious imported content, untrusted links and storage corruption; use strict CSP; no remote executable code; no request for all-sites access without a demonstrated requirement. Add privacy/deletion/export tests and package integrity checks. Respect commercial platform terms and user authorization.

7. Search, chapters and decisions

P0: lexical search over legitimately available messages, stable highlight/jump and useful snippets. P1: archive-backed full-text search with normalized tokens, references and filters. P2: optional semantic similarity search, with lexical fallback and original-source citations. No implicit equivalence between a semantic summary and an original quote.

Chapters: rule-based detection first (headings, topic transitions, chronology, explicit user organization); optional model proposals later. Allow split, merge, rename, reorder and cross-chapter references while retaining the original ordering and every message.

Decision timeline: introduced, confirmed, corrected, superseded, abandoned, contested and unknown are separate states. Never interpret most recent message as automatically globally authoritative; retain sources, applicability and corrections. Summaries or decision extractions require explicit provenance and may be disputed.

8. AI context rehydration (P3 only)

For a selected task, retrieve relevant chapter summaries, precise original passages, applicable corrections and recent conversation within a measured token budget. Show user exactly what will be sent, to which provider, and why. Record opt-in and source IDs. Prefer explicit absence/uncertainty over guessed history. Validate retrieval accuracy, stale-state handling and contradiction resolution against simple keyword-only baseline. Rehydration reduces irrelevant tokens; it does not increase the model's native context window.

10. Work order / implementation sequencing

  1. Inventory exact available provider UI and legal integration mechanisms; compare competitor workflow; record source links and date.
  2. Set up minimal MV3 extension and explicit permission model. No paid API or external services needed.
  3. Implement adapter message/heading indexing with coverage indicators and stable anchor recovery.
  4. Implement clickable outline, precise jump, highlighting, bookmarks and local search/persistence.
  5. Test long/virtualized chats and error cases; add automated fixtures and reproducible manual checks.
  6. Run timed comparison against native navigation and two competitors; preserve raw observations and report UNKNOWN where untested.
  7. Only after a credible P0, implement independent archive/book reader with verified import/export fidelity.

Completion report: commit/branch, browser version and supported provider, permission list, exact implemented features, screenshots or test recordings, test commands/results, known gaps, comparison measurements, and a reproducible install/rollback procedure. Distinguish code written, tests passing, live-browser confirmation, and public release. No agent or provider may claim success based solely on a sent assignment.

11. Multi-provider build governance

The owner requested Claude Opus 5.5 at xhigh effort, not Fast mode, for the extension. The appointed Foreman must verify model/effort actually supported before claiming it was used. Respect existing authorized sessions, budget/quotas, independent review and writer ownership. Do not change credentials, buy services, create unnecessary workflows or replace unrelated work. Preserve the owner's public-repository rule and check for secrets/private material before commits.

12. Roadmap, commercial criteria, and non-goals

Commercial hypothesis: People who revisit long AI discussions will value and potentially pay for durable original-response books and cross-conversation continuity beyond free chat-navigation tools. Validate with retention, retrieval performance and willingness-to-pay; no acquisition assumptions. Candidate customers: power users, developers, researchers, students and long-running project owners.

Not P0: universal provider history import, unrestricted private API access, generalized web scraping, cloud synchronization, external AI memory, agent orchestration, payment system or foundation model. Not ever promised: recovered inaccessible content, unchanged vendor interfaces, perfect semantic memory, guaranteed acquisition or exclusive originality.

Build versus reuse: reuse standard browser-extension, indexing, EPUB, and optional embedding tools when licenses permit. Do not reinvent generic retrieval infrastructure without clear measurable need. Require go/no-go evidence before investing in P2/P3.
